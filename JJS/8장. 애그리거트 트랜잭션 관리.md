# 8장. 애그리거트 트랜잭션 관리

## 한 줄 요약

같은 애그리거트를 동시에 수정할 때 일관성이 깨지지 않도록 **선점 잠금, 비선점 잠금, 오프라인 선점 잠금**으로 동시 접근을 제어한다.

## 학습 목표

- 애그리거트를 동시에 수정할 때 어떤 문제가 생기는지 설명할 수 있다.
- 선점 잠금과 비선점 잠금의 동작 방식과 차이를 이해한다.
- 선점 잠금에서 교착 상태가 생기는 이유와 대처 방법을 이해한다.
- 여러 트랜잭션에 걸친 충돌을 막기 위한 오프라인 선점 잠금을 이해한다.

## 1. 왜 필요한가

트랜잭션마다 리포지터리는 새 애그리거트 객체를 만든다. 그래서 두 스레드가 같은 애그리거트를 수정하면, **개념적으로는 같지만 물리적으로는 다른 객체**를 각자 고치게 된다. 한쪽의 변경을 다른 쪽이 모르는 채로 커밋하면 일관성이 깨진다.

→ 애그리거트 단위의 동시성 제어가 필요하다.

## 2. 선점 잠금 (비관적 락, Pessimistic Lock)
- 충돌이 날 거라고 비관적으로 보고, 미리 잠가서 다른 쪽의 접근을 막는다.
- **먼저 애그리거트를 구한 쪽이 끝날 때까지 다른 쪽의 접근을 막는다.**
- 기다리던 쪽은 잠금이 풀린 뒤 **변경된 최신 상태**를 보게 되므로 일관성이 유지된다.
- 보통 DBMS의 행 단위 잠금으로 구현한다.

### 교착 상태

- 두 스레드가 서로 상대가 가진 잠금을 기다리면 영원히 대기한다.
- 이를 막으려면 **잠금 최대 대기 시간**을 지정한다.

## 3. 비선점 잠금 (낙관적 락, Optimistic Lock)
충돌이 거의 없을 거라고 낙관적으로 보고, 잠그지 않은 채 반영할 때 버전으로 충돌만 확인하는 방법.

선점 잠금은 한 트랜잭션 안에서만 동작한다. **조회와 수정이 다른 트랜잭션**이면 오래된 정보를 보고 수정하는 문제를 막을 수 없다.

비선점 잠금은 **접근을 막지 않고, 반영 시점에 충돌했는지 확인한다.**

- 애그리거트에 **버전 값**을 두고 수정할 때마다 증가시킨다.
- 수정할 때 조회한 시점의 버전과 현재 버전이 다르면 충돌로 보고 실패시킨다.
- 여러 트랜잭션에 걸쳐 적용하려면 조회한 시점의 버전을 화면에 전달했다가 수정 요청 때 다시 받는다.

### 강제 버전 증가

- 루트가 아닌 내부 엔티티만 바뀌어도 **애그리거트 전체가 바뀐 것**이다.
- 따라서 이때도 루트의 버전을 강제로 증가시켜야 비선점 잠금이 올바르게 동작한다.

## 4. 오프라인 선점 잠금 (Offline Pessimistic Lock)

- **여러 트랜잭션에 걸쳐** 수정 시작부터 끝까지 다른 사용자의 수정을 막는다.
- **수정 화면을 열 때 잠금**을 얻고, **수정이 끝나면 해제**한다.
- 사용자가 잠금을 해제하지 않고 떠날 수 있으므로 **잠금 유효 시간**이 필요하다. 수정 중에는 유효 시간을 주기적으로 연장한다.
- 수정 요청 시 **잠금이 아직 유효한지 반드시 확인**한다. 그사이 만료되어 다른 사용자가 잠금을 가져갔을 수 있기 때문이다.

## 5. 정리

- **선점 잠금**: 한 트랜잭션 안에서 접근 자체를 막는다. 충돌이 잦을 때 쓴다.
- **비선점 잠금**: 버전으로 반영 시점에 충돌을 감지한다. 충돌이 드물 때 쓴다.
- **오프라인 선점 잠금**: 여러 트랜잭션에 걸쳐 편집하는 동안 충돌을 원천 차단한다.
