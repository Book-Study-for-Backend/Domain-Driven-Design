# 4장. 리포지터리와 모델 구현

## 한 줄 요약

리포지터리는 **애그리거트 단위로 도메인 객체를 저장하고 조회하는 창구**이다.

## 학습 목표

- JPA와 스프링 데이터 JPA로 리포지터리를 구현하는 방법을 비교할 수 있다.
- 엔티티와 밸류를 DDD 관점에 맞게 매핑하는 방법을 이해한다.
- 애그리거트의 로딩 전략, 영속성 전파, 식별자 생성 위치를 설명할 수 있다.

## 1. 리포지터리 구현 방법 두 가지

자바에서는 리포지터리를 다음 두 가지 방법으로 구현할 수 있다.

| 방법 | 설명 |
| --- | --- |
| JPA 직접 사용 | `EntityManager`를 이용해 조회·저장·삭제를 직접 구현한다. |
| 스프링 데이터 JPA | 인터페이스만 정의하면 스프링이 구현체를 자동으로 만들어 준다. |

### JPA를 이용한 리포지터리 구현

`EntityManager`는 JPA에서 영속성 컨텍스트를 다루는 객체다. 리포지터리 구현 클래스는 이를 이용해 애그리거트를 조회하고 저장한다.

**조회 기능**

- ID로 조회하는 메서드는 `findById`처럼 `findBy + 프로퍼티 이름` 형식으로 짓는 것이 일반적이다.
- 대상이 존재하지 않으면 `null`을 리턴한다. (`Optional`을 리턴하는 방식도 사용한다.)

**삭제 기능**

`delete(Order order)`로 애그리거트를 삭제할 수 있게 한다.

> 삭제 요구사항이 있어도 실제로 데이터를 지우는 경우는 많지 않다. 데이터 원복을 위해 일정 기간 보관해야 하거나, 관리자 기능에서 삭제된 데이터를 조회해야 할 수 있기 때문이다. 그래서 삭제 플래그를 두고 조회 대상에서 제외하는 방식을 많이 쓴다.

### 스프링 데이터 JPA를 이용한 리포지터리 구현

스프링 데이터 JPA는 `Repository` 인터페이스를 상속한 인터페이스를 찾아 구현 객체를 자동으로 스프링 빈으로 등록한다.

```java
public interface OrderRepository extends Repository<Order, OrderNo> {
    Optional<Order> findById(OrderNo id);
    void save(Order order);
    void delete(Order order);
}
```

`Repository<엔티티 타입, 식별자 타입>` 형태로 상속하고, 메서드 이름 규칙(`findBy...`, `save`, `delete` 등)에 맞춰 선언하면 된다.

## 2. 매핑 구현

여기부터는 스프링 데이터 JPA 매핑 내용이 중심이라, DDD 관점에서 신경 쓸 만한 내용만 정리한다.

- 밸류는 불변이므로 `set` 메서드를 제공하지 않는다.
- 상태를 바꿀 때는 `set` 대신 `changeShippingInfo()`처럼 의도가 드러나는 이름을 쓴다.

**AttributeConverter** (4.3.4)

두 개 이상의 프로퍼티를 가진 밸류 타입을 한 개의 컬럼에 매핑할 수도 있다. 예를 들어 `Length`의 `value`와 `unit`을 `"1000mm"` 같은 문자열 하나로 저장한다.

```java
public class Length {
    private int value;
    private String unit;
    ...
}
```

## 3. 애그리거트 로딩 전략

애그리거트 루트를 로딩하면 루트에 속한 모든 객체가 완전한 상태여야 한다.

다만 반드시 즉시 로딩을 해야 한다는 뜻은 아니다. 상태를 변경하는 시점에 필요한 객체를 사용할 수 있으면 되므로, 지연 로딩을 써도 트랜잭션 범위 안에서는 완전한 상태를 보장할 수 있다.

## 4. 애그리거트 영속성 전파

애그리거트의 조회·저장·삭제는 모두 하나의 단위로(원자적으로) 처리해야 한다.

- 저장: 루트만 저장하면 안 되고, 애그리거트에 속한 모든 객체를 저장한다.
- 삭제: 루트뿐 아니라 애그리거트에 속한 모든 객체를 삭제한다.

## 5. 식별자 생성 기능

식별자 생성 규칙은 도메인 규칙이므로 도메인 영역에 식별자 생성 기능을 둔다. 별도의 도메인 서비스로 분리해서 둘 수도 있다.
