# 2장. 아키텍처 개요

## 한 줄 요약

아키텍처는 각 영역의 책임과 의존 방향을 나누어, 핵심 도메인 규칙이 UI·DB 같은 기술에 휘둘리지 않게 만드는 구조다.

## 학습 목표

- 표현·응용·도메인·인프라스트럭처 네 영역의 역할을 이해한다.
- 계층형 아키텍처의 의존 방향과 DIP를 설명할 수 있다.
- 엔티티, 밸류, 애그리거트, 리포지터리, 도메인 서비스 등 도메인 영역의 구성요소를 구분할 수 있다.

## 네 개의 영역

| 영역 | 역할 |
| --- | --- |
| 표현 | 사용자의 요청을 받고 결과를 보여준다. |
| 응용 | 유스케이스의 흐름을 조정하고 트랜잭션을 처리한다. |
| 도메인 | 핵심 업무 규칙과 도메인 모델을 구현한다. |
| 인프라스트럭처 | 응용,도메인 계층이 필요로 하는 저장,조회,전송 기능을, 실제 사용하는 DB,외부 시스템,다른 모듈의 호출 방식과 데이터 형식에 맞춰 구현한다. |


## 계층형 아키텍처

일반적인 의존 방향은 다음과 같다.
상위 계층은 바로 하위 계층을 의존하는 편이지만 편리함을 위해 응용 계층이 인프라스트럭처 계층을 사용하기도 한다.

```
표현 영역
  ↓
응용 영역 ↘
  ↓
도메인 영역 → 인프라스트럭처
```


상위 계층은 하위 계층을 사용할 수 있지만, 도메인 영역이 표현 영역에 의존하면 안 된다. 도메인 모델이 컨트롤러, HTTP 요청, DB 기술을 알게 되면 핵심 규칙을 테스트하거나 다른 환경에서 재사용하기 어려워진다.

## DIP: 의존성 역전 원칙

도메인 영역이 DB 구현체를 직접 알면 도메인이 인프라스트럭처에 의존하게 된다. 이를 막기 위해 도메인 또는 응용 영역에 인터페이스를 두고, 인프라스트럭처가 이를 구현한다.

```
// 응용 영역이 필요로 하는 추상화
interface OrderRepository {
    fun findById(id: OrderId): Order?
    fun save(order: Order)
}

// 인프라스트럭처가 구현
class JpaOrderRepository : OrderRepository {
    // JPA를 이용해 구현
}
```

이렇게 하면 응용 서비스는 `JpaOrderRepository`가 아니라 `OrderRepository`에 의존한다. DB나 프레임워크가 바뀌어도 도메인 규칙과 응용 서비스의 변경을 줄일 수 있다.

이렇게하면 저수준 모듈(JpaOrderRepository)가 고수준 모듈(OrderRepository)에 의존하는 DIP 원칙이 적용된다.
구현 교체와, 테스트하기 쉬워지는 장점이있다.

### DIP 주의 사항
단순히 저수준 모듈에서 인터페이스를 하나 추가하는 것이 아니다.
고수준 **모듈**이 저수준 모듈에 의존하지 않게 하기 위함으로 인터페이스는 고수준 모듈 폴더 위치에 존재해야한다.

## 도메인 영역 주요 구성요소

| 구성요소 | 설명 |
| --- | --- |
| 엔티티 | 고유 식별자와 라이프사이클을 가진다. 도메인 데이터와 관련 기능을 함께 가진다. |
| 밸류 | 개념적으로 하나인 값을 표현하며, 불변이다. |
| 애그리거트 | 연관된 엔티티와 밸류를 묶어 일관성 경계를 책임진다. |
| 리포지터리 | 도메인 모델의 영속성을 처리한다. |
| 도메인 서비스 | 특정 엔티티에 속하지 않는 도메인 로직을 제공한다. |

리포지터리는 응용 서비스가 도메인 객체를 구하거나 저장할 때 사용한다. 트랜잭션은 응용 서비스가 관리하지만, 트랜잭션 처리 방식은 리포지터리 구현 기술의 영향을 받는다.

## 내가 이해한 흐름

아키텍처의 목적은 코드를 폴더별로 나누는 데 있지 않다. 변경 이유가 다른 코드를 분리하고, 가장 중요한 도메인 규칙이 외부 기술에 의존하지 않도록 하는 데 있다. 표현 영역은 요청을 받고, 응용 영역은 흐름을 조정하며, 도메인 영역은 규칙을 결정하고, 인프라스트럭처는 기술적인 세부 구현을 맡는다.

## 추가 조사 (AI 작성): 인프라스트럭처에는 무엇이 들어가는가 

### 리포지터리 말고도 들어가는 것들

인프라스트럭처에는 **외부 기술과 직접 연동하는 구현 코드**가 모두 들어간다.

| 종류 | 예시 |
| --- | --- |
| DB 연동 | JPA 리포지터리 구현, MyBatis 매퍼, 조회 전용 DAO 구현 |
| 다른 저장소 연동 | Redis 캐시, MongoDB, S3 같은 파일 저장소 |
| 메시징 | Kafka, RabbitMQ 메시지 송수신 |
| 외부 API 호출 | 결제 대행사(PG) 연동, HTTP 클라이언트로 REST API 호출 |
| 알림 발송 | SMTP 메일 발송, SMS, 푸시 알림 |
| 기타 기술 구현 | 룰 엔진(Drools), 암호화 라이브러리, 외부 인증 연동 |

어떤 기술이든 원칙은 DIP와 같다. **인터페이스는 도메인 또는 응용 영역에 두고, 구현만 인프라스트럭처에 둔다.**


### 인프라에서도 if를 써도 되는가

써도 된다. 기준은 if를 쓰느냐가 아니라 **그 if가 무엇을 결정하느냐**다.

- **비즈니스 규칙**("무엇을 해야 하나", "해도 되나") → 도메인
- **기술적 처리**("그걸 이 기술로 어떻게 하나") → 인프라

헷갈릴 때는 다음 질문으로 판단한다.

> **"이 기술(DB, Kafka, SMS 업체 등)을 다른 걸로 바꾸면 이 로직도 같이 사라지나?"**
> - 같이 사라진다 → 기술 처리 → 인프라
> - 기술을 바꿔도 여전히 지켜야 한다 → 비즈니스 규칙 → 도메인
>
> 보조 질문: **"기획자가 이 조건을 알아야 하나?"** 알아야 한다면 도메인이다.

| 코드 | 위치 | 이유 |
| --- | --- | --- |
| 배송중이면 주문 취소 불가 | 도메인 | 기술과 무관한 주문 규칙 |
| VIP 회원이면 10% 할인 | 도메인 | 기획자가 정하는 할인 정책 |
| 결제 실패면 주문을 결제 실패 상태로 변경 | 도메인 | 결제 결과에 따른 주문 규칙 |
| HTTP 응답이 503이면 3번까지 재시도 | 인프라 | 외부 API 통신 방식 |
| Redis에 캐시가 있으면 반환, 없으면 DB 조회 | 인프라 | 저장 기술 선택 |
| 결제사 응답 코드가 "0000"이면 성공으로 변환 | 인프라 | 특정 업체 API 형식 해석 |
| 문자가 90바이트를 넘으면 LMS로 전송 | 인프라 | SMS 기술의 제약 |

### 예시: 결제 연동

```
// 인프라: 결제사 API를 호출하고, 결과를 도메인이 이해하는 형태로 바꿔 돌려주기만 한다
class TossPaymentGateway : PaymentGateway {
    override fun pay(amount: Money): PaymentResult {
        val res = tossClient.request(...)
        if (res.code == "0000") return PaymentResult.success()   // 업체 형식 해석
        if (res.code == "E503") return retry(...)                // 통신 처리
        return PaymentResult.fail(res.message)
    }
}

// 도메인: 결과를 보고 "그래서 주문을 어떻게 할지"를 정한다
class Order {
    fun completePayment(result: PaymentResult) {
        if (result.isFail) { state = PAYMENT_FAILED; return }    // 비즈니스 규칙
        state = PAYMENT_DONE
    }
}
```

`TossPaymentGateway`의 if는 모두 "토스 API를 어떻게 다루나"에 대한 것이라, 결제사를 바꾸면 통째로 바뀐다. 반면 "결제 실패 시 주문 상태 변경"은 결제사를 바꿔도 남으므로 도메인에 있다.

### 잘못된 예

```
// ❌ SMS 발송 구현체 안에 비즈니스 규칙이 섞여 있음
if (member.isMarketingAgreed && order.total > 50000) {
    smsClient.send(...)
}
```

"마케팅 수신에 동의했고 5만 원 이상 주문한 회원에게만 발송"은 기획 정책이다. 이런 판단은 도메인이나 응용 서비스에서 끝내고, 인프라는 **보내라고 하면 보내기만** 해야 한다.

### 참고: 완벽한 분리를 고집하지 않는다

`@Transactional`, `@Entity` 같은 애노테이션까지 억지로 떼어 내면 구현이 오히려 복잡해진다. DIP의 장점(구현 교체, 테스트 용이성)을 해치지 않는 선에서 실용적으로 타협한다.

**정리: 인프라의 if는 "어떻게 할지"만 정하고, "할지 말지"는 도메인이 정한다.**

## 추가 조사 (AI 작성): 인프라스트럭처 판단 기준 더 파고들기

> AI와 문답한 내용을 정리한 것이다. 책 본문이 아니라 출판사 목차와 저자의 공식 예제 코드([madvirus/ddd-start2](https://github.com/madvirus/ddd-start2))를 근거로 했다.

### "기술적인 구현"을 구체적으로 풀면

> 응용·도메인 계층이 필요로 하는 저장·조회·전송 기능을, 실제로 쓰는 **DB·외부 시스템·다른 모듈의 호출 방식과 데이터 형식에 맞춰** 구현하는 것.

| 필요한 기능 | 인프라가 구현하는 구체적인 내용 |
| --- | --- |
| 애그리거트 저장 | 애그리거트를 DB 레코드로 변환하고, 테이블·키를 지정해 저장 명령 실행 |
| 애그리거트 조회 | DB 레코드를 읽어 애그리거트 객체로 복원 |
| 회원 정보를 주문에 사용 | 회원 조회 서비스를 호출하고 `MemberData`를 주문의 `Orderer`로 변환 |
| AI 응답 생성 | AI 업체 SDK에 맞춰 요청하고, 응답 스트림을 읽어 내부 형태로 파싱 |
| 메시지 발행 | 메시지를 JSON 등으로 직렬화해 지정된 메시지 큐로 전송 |

### 인프라가 연결하는 대상 세 가지

고정된 분류라기보다, **연결 대상만 다른 같은 역할**이다.

| 연결 대상 | 하는 일 |
| --- | --- |
| DB | 레코드를 읽어 애그리거트를 복원하거나, 변경 내용을 저장한다. (리포지터리 구현) |
| 다른 모듈 | 다른 모듈의 조회 서비스를 호출하고, 그 데이터를 우리 도메인 모델로 변환한다. |
| 외부 시스템 | HTTP·SDK·메시지 큐로 요청을 보내고 결과를 처리한다. |

공통점은 **구체적인 조회·저장·통신 방식과 데이터 변환**을 담당한다는 것이다. 객체를 만들지 않고 저장만 하거나 메시지만 보내는 구현도 포함된다.

### 저자 예제: `OrdererServiceImpl`

주문 도메인은 주문자 정보(`Orderer`)가 필요하지만, 회원 정보는 회원 모듈에 있다.

| 구분 | 위치 | 역할 |
| --- | --- | --- |
| `OrdererService` 인터페이스 | `order.command.domain` | "회원 ID를 주면 주문자 정보를 줘"라는 계약 |
| `OrdererServiceImpl` 구현체 | `order.infra` | 회원 모듈의 `MemberQueryService`를 호출 → `MemberData`를 받음 → `Orderer` 값 객체로 변환해 반환 |

이 클래스는 DB나 HTTP를 직접 호출하지 않는데도 `infra`에 있다. **회원 모듈의 조회 방식·모델과 주문 모델을 연결하는 것**이 역할이기 때문이다. 이름을 `MemberOrdererAdapter`로 바꿔 생각하면 역할이 더 잘 보인다.

DIP 구조도 그대로다.

```
응용 서비스 ──▶ 도메인 인터페이스(OrdererService) ◀── 인프라 구현체(OrdererServiceImpl)
```

- 도메인이 필요한 계약을 정의하고, 인프라가 그 계약을 구현한다. 실행 시에는 DI로 구현체가 주입된다.
- DIP가 모든 인터페이스를 도메인에 두라는 뜻은 아니다. 도메인에 필요한 계약은 도메인에, 응용 유스케이스에만 필요한 계약은 응용 계층에 둔다. **계약을 필요로 하는 상위 계층이 그 계약을 소유한다.**

### "Service"라는 이름이 계층을 정하지 않는다

이름에 `Service`가 붙어도 맡은 책임에 따라 계층이 달라진다. 주문 취소·환불 예시:

| 클래스 | 하는 일 | 계층 |
| --- | --- | --- |
| `CancelOrderService` | 주문 조회 → 환불액 계산 요청 → 환불 진행 → 취소 결과 저장 | 응용 |
| `RefundAmountService` | 주문 상태와 환불 정책에 따라 환불 가능 금액 계산 | 도메인 |
| `PgRefundService` | 결제사 API를 호출해 실제 환불 요청 | 인프라 |

- "이 주문은 9,000원 환불할 수 있다"고 **결정**하는 것 → 도메인
- 그 과정을 하나의 취소 작업으로 **진행**하는 것 → 응용
- "결제사에 9,000원 환불 요청을 **전송**"하는 것 → 인프라

`RefundService` 계약("이 결제에 이 금액을 환불해줘") 하나에 `A결제사RefundService`(SDK 호출), `B결제사RefundService`(HTTP API 호출)처럼 구현체가 여러 개일 수 있고, 이들은 모두 인프라다. 메일도 같다. "가입 후 환영 메일 발송"을 진행하는 건 응용, `SmtpMailService`·`ApiMailService`는 인프라다.

### 다른 서비스를 호출하면 인프라인가? → 아니다

"외부(다른 모듈)를 호출한다"는 사실만으로는 계층이 정해지지 않는다. 저자 예제의 `PlaceOrderService`(응용)도 상품 모듈의 `ProductRepository`를 호출한다.

| 클래스 | 맡은 책임 |
| --- | --- |
| 응용의 `PlaceOrderService` | 상품 조회 → 주문자 정보 확보 → 주문 생성 → 저장이라는 **주문 접수 작업을 진행** |
| 인프라의 `OrdererServiceImpl` | 회원 조회 기능을 호출하고 `MemberData`를 `Orderer`로 바꾸는 **연결 방법을 구현** |

핵심 차이는 **"다른 서비스를 호출한다"와 "그 서비스와 연결하는 방법을 책임진다"**의 차이다. 응용 서비스가 다른 서비스를 쓰는 건 자연스럽고, 매번 인프라 어댑터를 만들어야 하는 것도 아니다. 다른 모듈의 호출 방식과 데이터 변환을 별도 계약 뒤로 숨기기로 설계했을 때 인프라 구현체를 둔다.

### 판단 기준: 어떤 변경을 이 클래스가 떠안는가

| 변경 | 담당 |
| --- | --- |
| "주문 접수 전에 재고 예약도 해야 한다" | 응용 서비스 (작업 순서 변경) |
| "회원 정보를 가져오는 방법이 내부 메서드 호출에서 HTTP API로 바뀐다" | 인프라 어댑터 (연결 방법 변경) |
| "이런 상태의 회원은 주문할 수 없다" | 도메인 (허용 규칙 변경) |

### 인프라가 도메인 객체를 만들어도 되는가

된다. 리포지터리 구현체가 대표적인 예다. **객체가 속한 계층**과 **그 객체를 생성하는 코드의 계층**을 구분해야 한다.

- `Order`와 그 유효성 규칙 → 도메인
- DB 필드를 읽어 `Order(...)` 생성자에 넘기는 코드 → 인프라

단, 객체를 만든다는 이유만으로 인프라가 되지는 않는다. 외부 응답을 우리 모델로 변환하는 부분은 인프라가, 생성된 객체가 지켜야 할 규칙은 도메인 객체가 맡는다.

### AI 호출 예시

AI 채팅 서비스라면 역할이 이렇게 나뉜다.

| 역할 | 계층 |
| --- | --- |
| AI 모델을 호출하고 응답 스트림을 받아 파싱 | 인프라 |
| 대화 이력·프롬프트를 준비하고, 생성기를 호출하고, 결과를 저장 | 응용 |
| 대화 가능 여부, 턴 진행·종료 규칙, 상태 변경 | 도메인 |
| 결과를 클라이언트용 이벤트(WebSocket 등)로 구성 | 표현 |

"AI에게 **어떻게** 요청하고 응답을 받을까"는 인프라, "우리 채팅에서 **언제** 호출하고 결과를 **어떻게 처리**할까"는 응용·도메인이다.
