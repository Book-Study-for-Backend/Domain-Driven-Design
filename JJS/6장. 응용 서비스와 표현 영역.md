# 6장. 응용 서비스와 표현 영역

## 한 줄 요약

응용 서비스는 **도메인 객체를 조합해 사용자 요청을 처리하는 흐름만 담당하고**, 표현 영역은 **사용자 요청을 응용 서비스가 이해할 수 있는 형태로 바꾸는 역할**을 한다.

## 학습 목표

- 표현 영역과 응용 영역이 각각 어떤 역할을 하는지 설명할 수 있다.
- 응용 서비스에 도메인 로직을 넣으면 안 되는 이유를 이해한다.
- 응용 서비스의 크기, 파라미터와 리턴 타입, 트랜잭션 처리 방법을 이해한다.
- 값 검증과 권한 검사를 어느 영역에서 해야 하는지 설명할 수 있다.



## 1. 표현 영역과 응용 영역
- 표현 영역 : 유저의 요청을 받고 변환하여 원하는 기능에 연결시키고, 알맞은 형태로 응답한다.
- 응용 영역 : 표현 영역에서 온 요청을 통해 도메인 객체를 사용해 원가는 기능을 제공한다.

- 표현 영역은 HTTP 요청 파라미터처럼 사용자마다 다른 입력 형식을 응용 서비스가 요구하는 형식으로 변환한다.
- 응용 영역은 사용자가 웹 브라우저로 요청했는지, REST API로 요청했는지 알 필요가 없다. 기능 실행에 필요한 값만 받으면 된다.


## 2. 응용 서비스의 역할

응용 서비스는 사용자의 요청을 처리하기 위해 **리포지터리에서 도메인 객체를 가져와 사용**한다. 즉, 응용 서비스는 도메인 영역과 표현 영역을 연결하는 역할을 한다.

응용 서비스는 **트랜잭션 처리**와 **접근 제어, 이벤트 처리** 같은 일도 담당한다.

### 도메인 로직 넣지 않기

도메인 로직은 도메인 영역에 두고, 응용 서비스는 도메인 로직을 구현하지 않는다.

예를 들어 암호 변경 기능에서 "기존 암호가 맞는지 확인"하는 것은 도메인의 핵심 로직이다. 이를 응용 서비스에서 구현하면 다음 문제가 생긴다.

- **코드의 응집성이 떨어진다.** 도메인 데이터와 그 데이터를 조작하는 로직이 서로 다른 영역에 흩어져, 도메인 로직을 파악하려면 여러 영역을 뒤져야 한다.
- **여러 응용 서비스에서 같은 로직을 중복 구현할 가능성이 높아진다.** 암호 확인 로직이 필요한 다른 기능(예: 회원 탈퇴)에서도 같은 코드를 또 작성하게 된다.

결국 두 문제 모두 **코드 변경을 어렵게 만든다.** 

## 3. 응용 서비스의 구현

### 응용 서비스의 크기

회원 도메인을 예로 들면, 응용 서비스를 구성하는 방법은 두 가지다.

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 한 클래스에 관련 기능 모두 구현 (`MemberService`) | 동일 로직의 중복을 제거하기 쉽다. | 클래스 크기가 커지고, 관련 없는 코드가 뒤섞여 코드를 이해하기 어려워진다. |
| 기능별로 클래스 분리 (`ChangePasswordService`) | 클래스 개수는 많아지지만, 코드 품질을 일정 수준으로 유지하기 쉽다. | 공통 로직은 별도 클래스로 빼야 한다. |

책의 저자는 한 클래스가 여러 역할을 갖는 것보다 **구분되는 기능별로 서비스 클래스를 나누는 방식**을 선호한다. 중복되는 로직은 별도 헬퍼 클래스에 두고 재사용한다.

### 응용 서비스의 인터페이스와 클래스

응용 서비스를 인터페이스와 구현 클래스로 무조건 나눌 필요는 없다.

- 구현 클래스가 여러 개인 경우라면 인터페이스가 필요하지만, 응용 서비스는 보통 런타임에 구현을 교체할 일이 거의 없다.
- **인터페이스가 명확하게 필요하기 전까지는 인터페이스를 따로 만들지 않는 편이 낫다.**
- 테스트를 위해 표현 영역에서 응용 서비스를 대역으로 바꿔야 한다면, 인터페이스 대신 Mockito 같은 대역 도구를 사용하면 된다.

### 메서드 파라미터와 값 리턴

- 응용 서비스는 기능 실행에 필요한 값을 파라미터로 받는다. 값이 많으면 별도의 데이터 클래스 로 묶어 받는다.
- 리턴 값은 표현 영역에서 필요한 데이터만 돌려준다.
- **애그리거트 자체를 리턴하지 않는다.** 애그리거트를 리턴하면 표현 영역에서도 도메인 로직을 실행할 수 있게 되어, 기능 실행 로직이 응용 영역과 표현 영역에 분산된다.

### 표현 영역에 의존하지 않기

응용 서비스의 파라미터 타입으로 `HttpServletRequest`, `HttpSession` 같은 표현 영역 기술을 쓰지 않는다.

- 응용 서비스만 단독으로 테스트하기 어려워진다.
- 표현 영역의 구현이 바뀌면 응용 서비스도 함께 바뀌어야 한다.
- 응용 서비스가 세션 값을 직접 바꾸는 등, 표현 영역이 책임져야 할 상태 관리를 응용 서비스가 하게 되어 코드 응집도가 떨어진다.

### 트랜잭션 처리
- 사용자 요청 하나의 기능은 하나의 트랜잭션 안에서 처리되어야 한다. 일부만 반영되면 데이터 일관성이 깨진다.

## 4. 표현 영역

표현 영역의 책임은 크게 세 가지다.

1. **사용자가 시스템을 사용할 수 있는 흐름(화면)을 제공하고 제어한다.**
   - 게시글 쓰기 요청이 오면 입력 폼을 보여 주고, 폼 전송 요청이 오면 응용 서비스를 호출해 게시글을 등록한다.
2. **사용자의 요청을 알맞은 응용 서비스에 전달하고 결과를 사용자에게 제공한다.**
   - 요청 데이터를 응용 서비스가 요구하는 형식으로 변환하고, 결과를 응답 형식(HTML, JSON 등)으로 변환한다.
   - **응용 서비스에서 발생한 예외도** 사용자에게 알맞은 형태로 바꿔서 알려 준다.
3. **사용자의 세션을 관리한다.**
   - 로그인 상태 유지처럼 사용자 연결 상태를 관리하는 것은 표현 영역의 몫이다.

## 5. 값 검증

값 검증은 표현 영역과 응용 서비스 두 곳에서 모두 수행할 수 있다. 원칙적으로는 **모든 값에 대한 검증을 응용 서비스에서 처리**한다.

- 응용 서비스에서 검증 실패 시 예외를 바로 던지면, 사용자는 첫 번째 오류 하나만 알 수 있어 불편하다.
- 표현 영역에서 필수 값 검증을 먼저 하고, 응용 서비스에서는 논리적 오류만 검증하는 방식으로 나눌 수도 있다.

| 영역 | 검증 대상 |
| --- | --- |
| 표현 영역 | 필수 값, 값의 형식, 범위 등 |
| 응용 서비스 | 데이터의 존재 유무와 같은 논리적 오류 |

> 응용 서비스를 사용하는 표현 영역 코드가 한 곳이면 구현의 편리함을 위해 역할을 나눌 수 있다. 하지만 응용 서비스를 실행하는 주체가 다양하면(웹, API, 배치 등) 응용 서비스에서 반드시 파라미터로 전달받은 값이 올바른지 검사해야 한다.
