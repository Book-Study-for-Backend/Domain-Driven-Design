# 2.1. 네 개의 영역
- 표현, 응용, 도메인, 인프라스트럭처는 아키텍처를 설계에서 보편적으로 사용되는 전형적인 영역이다.
- 표현 영역은 사용자의 요청을 받아 응용 영역에 전달하고 응용 영역의 처리 결과를 다시 사용자에게 보여주는 역할을 한다.
	- 스프링 MVC 프레임워크가 표현 영역을 위한 기술에 해당한다.
- 표현 영역은 HTTP 요청을 응용 영역이 필요로 하는 형식으로 변환해서 응용 영역에 전달하고 응용 영역의 응답을 HTTP 응답으로 변환하여 전송한다.
	- 응용 영역은 로직을 직접 수행하기보다는 도메인 모델에 로직 수행을 위임한다.
	- 도메인 영역은 도메인의 핵심 로직을 구현한다. 예시로 주문 도메인은 아래의 것을 구현할 수 있다.
		- 배송지 변경
		- 결제 완료
		- 주문 총액 계산 
	- 인프라스트럭처 영역은 구현 기술에 대한 것을 다룬다. RDBMS 연동을 처리하거나, 메시징 큐에 메시지를 전송하거나 수신하는 기능을 구현하고, 데이터 연동을 처리한다.

# 2.2. 계층 구조 아키텍처
- 네 영역을 구성할 때 많이 사용되는 아키텍처는 계층 구조 아키텍처다.
	- 계층 구조 특성상 상위 계층에서 하위 계층으로의 의존만 존재하고 상위 계층에 의존하지 않는다.
- 엄격하게 적용하면 상위 계층은 바로 아래 계층에만 의존을 가져야 한다.
	- 다만, 구현의 편리함을 위해 계층 구조를 유연하게 적용할 수 있다. 모든 상황에 맞는 구조는 없다.
- 유연한 구조를 위해서 많은 것을 허용하면 아키텍처를 도입한 이유가 없어진다.
	- 의존성은 점점 복잡해지고 서로 얽히고 하나를 수정하면 여럿을 수정하는 일이 발생하게 된다.
	- 이러한 문제를 축소하는 방법은 DIP다.

# 2.3. DIP
- 가격 할인 계산을 예시로 들어보자. 고객 정보를 구하고 정책을 적용해야 한다.
	- 가격 할인 계산을 담당하는 클래스는 CalculateDiscountService로, 고수준 모듈이다.
		- 고수준 모듈은 의미 있는 단일 기능을 제공하는 모듈을 의미한다.
	- 가격 할인 계산을 하기 위해서는 고객 정보를 가져오고 할인 정책을 적용한다. 저수준 모듈을 통해서 고객 정보를 가져오고 할인 정책을 가져와야한다.
		- 저수준 모듈은 하위 기능을 실제로 구현한 것을 의미한다.
	- 고수준 모듈이 기능을 제공하기 위해서는 저수준 모듈에 의존하는 현상이 발생한다. 하지만, 앞서 말한 문제가 발생할 수 밖에 없다.
- 반대로 저수준 모듈이 고수준 모듈에 의존하도록 만든다.
	- 고수준 모듈 입장에서는 원하는 정보가 제공된다면, 어떤 방법이어도 문제 없다.
	- 추상화된 인터페이스를 저수준 모듈이 의존하도록 만들고, 고수준 모듈에서는 인터페이스를 사용한다.

## 2.3.1. DIP 주의사항
- DIP의 핵심은 고수준 모듈이 저수준 모듈에 의존하지 않는 것이다.
	- 저수준 모듈의 인터페이스를 추출하는 것이 아니라, 고수준 모듈의 인터페이스를 추출해야 한다.

# 2.4. 도메인 영역의 주요 구성요소
| 요소                      | 설명                                                                  |
| ----------------------- | ------------------------------------------------------------------- |
| 엔티티(Entity)             | 고유 식별자를 가지고 자신만의 라이프사이클을 보유한다.                                      |
| 밸류(Value)               | 고유 식별자를 가지지 않으며, 개념적으로 하나인 값을 표현할 때 사용한다.                           |
| 애그리거트(Aggregate)        | 연관된 엔티이와 밸류 객체를 개념적으로 묶은 것을 의미한다.                                   |
| 리포지터리(Repository)       | 도메인 모델의 영속성을 처리한다.                                                  |
| 도메인 서비스(Domain Service) | 특정 엔티티에 속하지 않은 도메인 로직을 제공한다. 여러 엔티티와 밸류를 필요로 하면 도메인 서비스에서 로직을 구현한다. |

## 2.4.1. 엔티티와 밸류
- DB 테이블의 엔티티와 도메인 모델의 엔티티는 동일한 것이 아니다.
	- 가장 큰 차이점은 도메인 모델의 엔티티는 데이터와 함께 도메인 기능을 제공한다는 것이다.
	- 다른 차이점은 도메인 모델의 엔티티는 두 개 이상의 데이터가 개념적으로 하나인 경우 밸류 타입을 이용해서 표현할 수 있다.

## 2.4.2. 애그리거트
- 도메인 모델이 복잡해지면 개발자가 구조 맥락을 파악하기 어렵다.
- 애그리거트를 통해서 도메인 모델의 전체 구조를 파악하는 것에 도움을 받을 수 있다.
	- 애그리거트는 관련 객체를 하나로 묶은 군집이기 때문.

## 2.4.3. 리포지터리
- 물리적인 저장소에 도메인 객체를 보관해야 한다. 이를 위한 도메인 모델이 리포지터리다.
	- 구현을 위한 도메인 모델을 의미한다.
	- 애그리거트 단위로 도메인 객체를 저장하고 조회하는 기능을 정의한다.

# 2.5. 요청 처리 흐름
- 표현 영역은 사용자가 전송한 데이터의 형식을 검사하고 문제가 없다면 응용 서비스에 기능 실행을 위임한다.
	- 이때 응용 서비스가 요구하는 형식으로 변환해서 전달한다.
- 응용 서비스는 도메인 모델을 이용해서 기능을 구현한다. 기능 구현에 필요한 도메인 객체를 가져와 실행하거나 신규 도메인 객체를 실행해, 리포지터리에 저장한다.

# 2.6. 인프라스트럭쳐 개요
- 인프라스트럭쳐는 표현 영역, 응용 영역, 도메인 영역을 지원한다.
	- 도메인 영역과 응용 영역에서 직접 인프라스트럭처를 호출하는 것 보다 인터페이스를 사용하는 것이 시스템을 더 유연하게 만든다.
