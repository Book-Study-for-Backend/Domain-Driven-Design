# 8.1. 애그리거트와 트랜잭션
- 한 주문 애그리거트를 운영자와 사용자가 동시에 수정하게 된다면 문제가 발생한다.
	- 트랜잭션마다 리포지터리는 새로운 애그리거트 객체를 생성하므로, 같은 ID를 바라보는 다른 객체를 구하게 된다.
	- 그렇다면, 운영자와 사용자가 동시에 값을 수정하면 일관성이 어긋나게 된다.
- 일관성을 확보하기 위해서 아래 방법을 사용할 수 있다.,
	- 배송지 정보를 조회하고 상태를 변경하는 동안 사용자가 애그리거트를 수정하지 못하게 한다.
	- 운영자가 배송지 정보를 조회한 이후에 사용자가 정보를 변경하면 운영자가 애그리거트를 다시 ㅗㅈ회한 뒤 수정하도록 한다.
- 이러한 내용들은 애그리거트 자체의 트랜잭션과 관련 있다. 
	- 애그리거트에 대해 사용할 수 있는 대표적인 트랜잭션 처리 방법에는 `선점`과 `비선점` 잠금이 있다.

# 8.2. 선점 잠금
- 선점 잠금은 애그리거트를 구한 스레드가 사용을 끝마칠 때까지 다른 스레드가 접근할 수 없도록 잠그는 방식이다.
	- 이미 애그리거트가 선점되었다면, 다른 스레드는 블로킹 상태로 존재한다.

## 8.2.1. 선점 잠금과 교착 상태
- 선점 잠금에서는 교착 상태가 발생하지 않도록 주의해야 한다.
	- 스레드 1과 스레드 2가 서로 하나의 애그리거트를 선점하고, 다른 스레드가 보유한 애그리거트를 흭득하려고 할 때 발생한다.
	- 두 스레드는 서로 가진 자원을 탐하고 있기에 도달할 수 없게 된다.
- 교착 상태는 잠금을 구할 때 최대 대기 시간을 지정하는 방법으로 해소할 수 있다.

# 8.3. 비선점 잠금
- 선점 잠금은 강력하지만, 모든 문제를 해결할 수 있는 것은 아니다.
	- 운영자가 배송지 정보에 관련된 애그리거트 락을 건다.
	- 운영자는 모든 작업이 끝나 락을 해제한다.
	- 사용자가 방문해서 배송지 정보에 관련된 애그리거트 락을 걸고 값을 수정한다.
	- 운영자가 알고 있던 정보와 달라지게 된다.
- 이런 문제들을 해소하기 위해서 운영자는 액션을 취하기 전에 다시 한 번 값을 확인하도록 해야한다.
	- 비선점 잠금을 통해서 구현할 수 있다.
- 애그리거트에 버전을 사용할 숫자 타입 프로퍼티를 추가하고 애그리거트 수정 시 버전으로 사용할 프로퍼티 값을 1씩 증가시킨다.
	- DB에 있는 버전 정보가 신규 버전보다 한 단계 이전 버전이라면 수정하고 아니라면 실패하게 한다.

## 8.3.1. 강제 버전 증가
- 애그리거트에 애그리거트 루트 외의 다른 엔티티가 하나 있다고 가정하고, 해당 엔티티의 값만 변경되더라도 루트 엔티티의 버전은 증가해야 한다.

# 8.4. 오프라인 선점 잠금
- 오프라인 선점 잠금은 여러 트랜잭션에 걸쳐서 동시 변경을 막는다. 
	- 첫 트랜잭션에서 잠금을 선점한다.
	- 마지막 트랜잭션에서 잠금을 해제한다.
	- 잠금 헤제 전까지 다른 사용자는 잠금을 구할 수 없다.
